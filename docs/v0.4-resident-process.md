# MyPhone v0.4 — 常驻进程（后台保活 + 来电唤醒）设计

> 版本: v0.4 · 日期: 2026-08-10
> 决策: 原生前台服务独占 WebSocket；Flutter 通过通道桥接接入

---

## 一、目标

> 原需求: "app 启动后，有一个进程常驻内存，后面即使 app 退出，常驻进程负责保持登录和来电唤醒 app 方便接听。"

1. **常驻** — app 启动/登录后拉起前台服务，上滑退出 app 后服务仍存活。
2. **保持登录** — 服务独占 WebSocket 信令连接（心跳 + 断线重连），用户始终显示"在线"，来电随时可达。
3. **来电唤醒** — 服务收到来电 `offer` 时：立即响铃、震动、全屏来电，并把 app 拉起到接听界面。

---

## 二、现状与约束

| 项 | 现状 | 对设计的影响 |
|----|------|-------------|
| 信令连接 | `CallStateNotifier` 持有 `SignalingClient`（Dart WebSocket 直连 `/ws`） | WS 的生命周期 == Flutter 进程生命周期，进程一死就掉线 |
| 服务端 hub | `clients map[userID]` 一个用户只保留一条连接，新连接顶掉旧连接（hub.go:63） | 服务端**零改动**；但 app 和服务不能同时持有两条 WS |
| 在线状态 | Presence 即"WS 是否活着" | 服务独占 WS ⇒ 服务活着 = 在线 |
| 登录态 | token 存 Secure Storage（进程被杀不丢） | 服务重启后拿 token 重连即可，无需重新登录 |
| 来电界面 | 已有 `incoming_call_screen.dart` + `ringtone_service.dart` + E2EE 协商 | **复用**，不做原生接听 UI |

**核心结论**：
- "常驻进程"在 Android 上的标准实现是**前台服务（Foreground Service）**——它把 app 进程"钉住"，上滑杀界面也不会被杀，同时必须显示一条常驻通知。
- 服务端只认一条 WS/用户 ⇒ **WS 必须始终由服务独占**，Flutter 前台时也只是"接入服务"，不另开 WS。这避免了"app 和服务谁在线"的握手竞态。
- app 进程被杀后，Flutter/Dart 状态全部消失，所以**WS 与来电检测必须在原生侧**，不依赖 Dart 存活。

## 三、总体架构

```
┌────────────────────────── Android 进程 ──────────────────────────┐
│                                                                  │
│  ┌─────────────────────────────┐      ┌──────────────────────┐  │
│  │       Flutter (UI / WebRTC) │      │  CallService (Java)  │  │
│  │                             │      │  前台服务(独占WS)     │  │
│  │  ServiceBridgeSignaling     │◄────►│  OkHttp WebSocket     │──► /ws (信令)
│  │  (MethodChannel 发送        │      │  心跳15s+重连退避      │  │
│  │   EventChannel 接收)        │      │  常驻通知             │  │
│  │                             │      │  来电全屏+响铃+震动   │  │
│  │  incoming_call_screen       │      │  token 持有/登出清理  │  │
│  │  ringtone_service           │      │                      │  │
│  └─────────────────────────────┘      └──────────────────────┘  │
│                                                                  │
│              ▲ WebRTC 媒体面直连（P2P / TURN），不经过服务       │
└──────────────────────────────────────────────────────────────────┘
```

- **服务独占 WebSocket**：所有信令（offer/answer/ICE/e2ee/hangup/busy）都走服务这一条连接。
- **Flutter 是服务的"客户端"**：
  - Flutter → 服务：`MethodChannel("myphone/service")` — `sendSignal`、`setToken`、`setAppActive`、`logout`。
  - 服务 → Flutter：`EventChannel("myphone/service_events")` — 推流收到的信令。
  - 冷启动：来电 `fullScreenIntent` 的 extras 携带 offer 数据，Flutter 启动后读取并注入 `incomingCallProvider`（复用现有"收到来电自动 push 到 /incoming-call"的逻辑）。
- **WebRTC 媒体面**（语音流）仍是 Flutter 侧直连对端，不经过服务。

## 四、原生前台服务设计（CallService）

### 4.1 职责

| 职责 | 说明 |
|------|------|
| 独占 WS | OkHttp WebSocket 连 `ws://host:port/ws?token=...`；协议与现有 `SignalingClient` 完全一致 |
| 心跳/重连 | 每 15s 发 `{"type":"ping"}`；断线重连退避 2s/4s/8s/16s/30s（与现有实现一致） |
| 保持在线 | WS 活着 ⇒ 服务端 presence 恒为在线 ⇒ "保持登录" |
| 来电检测 | 收到 `offer` 后按 §6 时序处理 |
| 常驻通知 | 低优先级通知（"MyPhone 正在运行，保持来电在线"） |
| token 自举 | 内存持有 Flutter 注入的 token；重启后从安全存储读取（见 4.4） |

### 4.2 WS 协议复用

- 收到的消息 JSON 格式与现有 `CallSignal.fromJson` 完全一致，服务只做**透传 + offer 拦截**，不解密不解析业务字段。
- 发送侧：Flutter 通过 `sendSignal` 把序列化好的 JSON 字符串交给服务，服务原样写到 WS。
- `CallSignal` 编解码仍只存在 Flutter 侧一份；原生侧只按 `type` 字段判断是否 `offer`（用于触发来电）。

### 4.3 生命周期

- `onStartCommand` 返回 **START_STICKY**：被系统杀掉后自动重启。
- **开机自启**（可选，M4）：`BOOT_COMPLETED` 广播 → 若安全存储存在 token 则拉起重连。
- 通知渠道：
  - `resident` — 常驻，IMPORTANCE_LOW，无声音无震动。
  - `incoming_call` — 来电，IMPORTANCE_HIGH，带 fullScreenIntent + 声音 + 震动。
- 服务进程被国产 ROM 杀死的对策见 §9。

### 4.4 token 获取与登出

| 场景 | 取 token 方式 |
|------|--------------|
| app 启动/登录（主路径） | Flutter 登录后经 `setToken` 注入服务，服务内存持有 |
| 服务被系统重启（START_STICKY） | 服务从原生 `EncryptedSharedPreferences` 自举读取（与 flutter_secure_storage 同一存储，实施时核对文件名/前缀） |
| 用户登出 | Flutter 调 `logout` → 服务断 WS（离线）、清内存 token、停止常驻服务 |

> 实施风险：`flutter_secure_storage(encryptedSharedPreferences: true)` 在原生侧的存储键名/文件名需核对。若不可行，退化为"登出后 token 不持久、重启后需 app 重新注入"（开机自启项相应降级）。

## 五、Flutter 信令层重构

### 5.1 SignalingClient 抽象

把现有 `SignalingClient` 拆成协议层 + 两种传输实现：

```
CallSignalCodec (纯编解码，复用现有 CallSignal.fromJson/toJson)
        │
        ├── DirectWSSignalingClient   ← 现有实现（iOS / 桌面 / 测试 / 常驻关闭时 Android）
        │       自带 WebSocket + 心跳 + 重连
        └── ServiceBridgeSignalingClient ← Android 常驻开启时
                sendSignal  → MethodChannel 交给 CallService
                信令流        → EventChannel 接收（offer/answer/ICE/...）
```

- `CallStateNotifier` 只依赖抽象接口，业务逻辑（E2EE、WebRTC、busy 等）**零改动**。
- 关键不变量：**Android 常驻开启时全链路只有服务一条 WS**；Flutter 永不再建 WS。

### 5.2 冷启动来电注入

- 服务经 `fullScreenIntent` 启动 `MainActivity` 时，extras 携带：
  `callId / fromUserId / toUserId / contactName / sdp / e2eeOffer`。
- Flutter 启动后调用 `getIntentExtras()`（MethodChannel）读取，解析为 `PendingIncomingCall` 注入 `incomingCallProvider`。
- 现有 `MyPhoneApp` 对 `incomingCallProvider` 的 `ref.listen` 已会自动 push 到 `/incoming-call`，**导航逻辑无需改**，只需新增"启动时注入"一步。

### 5.3 app 活跃度上报

- Flutter 通过 `WidgetsBindingObserver` 监听生命周期：
  - `resumed` → `setAppActive(true)`
  - `paused/hidden` → `setAppActive(false)`
- 服务据此决定来电呈现方式（§6）。
- **心跳兜底**：Flutter 每 10s 调 `ping` 上报；服务 >25s 未收到则视为 app 已死（`appActive` 强制为 false）。防止"进程被杀但标志停留为 true"导致的来电被吞。

## 六、来电唤醒时序

```
对端拨号
   │  offer ──────────────────────────────► CallService WS
   ▼
CallService 收到 offer
   ├─ 判断 appActive
   │
   ├─ [app 前台]  EventChannel 推 offer → Flutter 现有 ringtone_service 响铃
   │              → incoming_call_screen 弹出（复用现有全部逻辑，无原生 UI）
   │
   └─ [app 后台/被杀]  ① 立即原生响铃 + 震动（覆盖 Flutter 冷启动 ~1-3s 空窗）
                      ② 发全屏来电通知（fullScreenIntent → MainActivity + extras）
                      ③ 同时 EventChannel 推 offer
                      → Flutter 启动/回前台 → 读 extras → 注入 incomingCallProvider
                      → incoming_call_screen 接管 → 停原生响铃
接听 → Flutter acceptIncomingCall（WebRTC + E2EE，现有流程）→ 媒体直连对端
拒绝 → Flutter 发 busy（经服务）→ 服务停响铃、撤来电通知
超时 → 响铃 30s 无应答 → 服务自动撤通知 + 发 busy（对齐主叫侧现有超时逻辑）
```

设计要点：
- **不实现原生接听/拒绝 UI**，一律拉起 Flutter 复用现有来电界面；原生侧只负责"立刻出声 + 拉进程"，把 ~1-3s 的 Flutter 冷启动空窗用原生响铃盖住。
- app 被杀时来电：全屏来电通知即"唤醒 app 方便接听"的落点（锁屏/任意 app 之上都会弹出，同系统电话）。

## 七、Android 平台清单

### 7.1 Manifest 权限与声明

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE"/>
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_PHONE_CALL"/> <!-- API34+ -->
<uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>              <!-- API33+ 运行时 -->
<uses-permission android:name="android.permission.USE_FULL_SCREEN_INTENT"/>
<uses-permission android:name="android.permission.VIBRATE"/>
<uses-permission android:name="android.permission.WAKE_LOCK"/>
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED"/>

<service
    android:name=".CallService"
    android:exported="false"
    android:foregroundServiceType="phoneCall"
    android:stopWithTask="false"/>
<receiver
    android:name=".BootReceiver"
    android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED"/>
    </intent-filter>
</receiver>
```

- `foregroundServiceType="phoneCall"`：系统允许后台启动前台服务（Android 12+ 对 phoneCall 类型豁免后台启动限制），且来电场景语义正确。自签名 sideload 不受 Google Play 对 USE_FULL_SCREEN_INTENT 的限制。
- `POST_NOTIFICATIONS` 需 API 33+ 运行时申请（沿用现有 `permission_handler`）。

### 7.2 启动/停止时机

| 时机 | 动作 |
|------|------|
| 登录成功 | `startForegroundService` 拉起服务，`setToken` 注入 |
| 用户登出 | `logout` → 服务断 WS 并 `stopSelf` |
| 设置"常驻保持在线"关闭 | 停止服务；app 回退 `DirectWSSignalingClient`（仅前台在线，等同现状） |
| 开机 | `BootReceiver` → 有 token 则拉服务重连（M4） |

## 八、设置项与用户引导

- **"常驻后台（保持在线）"开关**（默认开）：
  - 开 ⇒ 服务独占 WS，后台/杀进程仍在线，来电全屏唤醒。
  - 关 ⇒ 仅 app 前台在线，等同当前 v0.3 行为。
- **"加入电池白名单"引导按钮**：跳到系统电池优化设置 + 逐 ROM 指引（小米/华为/OPPO/vivo/一加 的"自启动/后台运行/电池白名单"路径）。
- **常驻通知不可关闭**（系统强制），文案写清用途，降低用户困惑。

## 九、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 国产 ROM 电池管理杀服务 | 常驻失效，来电不响 | §8 白名单引导；START_STICKY + 开机自启兜底；服务内自监测被杀死时（onDestroy 非自杀）提示用户 |
| Flutter 冷启动 ~1-3s 空窗 | 来电后响铃前有静默 | 原生立即响铃盖住空窗，Flutter 接管后停原生响铃 |
| app 进程被杀但 `appActive` 标志残留 | 来电被当成"前台"而吞掉 | §5.3 心跳兜底 + EventChannel 断连判定 |
| 双 UI 竞争（原生 vs Flutter 来电界面） | 出现两个来电界面 | 本设计不建原生接听 UI，前台一律 Flutter 界面，无竞争 |
| token 跨原生/Flutter 存储读取 | 服务重启后无法自举 | §4.4 核对 EncryptedSharedPreferences 键名；必要时退化为 app 注入 |
| 通话中上滑杀 app | 通话中断 | 前台服务保住进程（顺带增强），但通话 UI 本身须前台，列为已知限制 |
| 双 WS 连接 | 服务端顶替导致掉线 | 架构上杜绝：Flutter 永不开 WS，只经桥接 |

## 十、验收标准（可验证）

1. **常驻**：登录后上滑杀掉 app → 服务通知仍在，`ps` 可见进程；另一账号查 presence 该用户仍"在线"。
2. **保持登录**：杀 app 后等待 >60s，服务 WS 未断、心跳正常；断网 30s 再恢复 → 自动重连成功。
3. **来电唤醒（app 被杀）**：另一账号拨号 → 全屏来电 + 响铃 → 接听 → 通话建立（WebRTC 媒体双向正常），界面走现有 call_screen。
4. **来电（app 前台）**：直接弹 Flutter 来电界面响铃，无原生全屏、无双 UI。
5. **不接超时**：响铃 30s 无应答 → 自动挂断，主叫方收到失败。
6. **拒绝**：点拒绝 → 对端收到 busy。
7. **登出**：登出后 presence 变离线，服务停止。
8. **ROM 引导**：设置页"加入电池白名单"入口可达、文案正确。
9. **冷启动来电 E2EE**：来电走完 E2EE 协商，通话锁标识正确显示（对齐现有 E2EE 报告）。

## 十二、非目标（明确不做）

- 原生接听/拒绝来电 UI（一律走 Flutter 现有界面）。
- 通话中切到后台仍保通话（需原生 WebRTC，超 v0.4 范围）。
- 服务端多连接/多端支持（单连接模型已满足，服务端零改动）。
- iOS 后台模式（本版只做 Android；iOS 需 VoIP push，另行规划）。
